# Техническое задание: FS25 AI Unload Threshold

**Для:** Codex (автономная реализация проекта)  
**Игра:** Farming Simulator 25 (FS25)  
**Тип:** Lua script mod  
**Рабочее имя / ZIP:** `FS25_AIUnloadThreshold` / `FS25_AIUnloadThreshold.zip`  
**Целевая платформа:** macOS, одиночная игра  
**Приоритет:** минимальное вмешательство в штатное поведение игры

## 1. Проблема и цель

При уборке урожая игрок вручную перегружает зерно из комбайна в прицеп, а штатный AI Worker выполняет задание **Deliver** с циклическими рейсами. В FS25 работник продолжает ждать загрузку, пока прицеп не заполнится на 100%. Например, комбайн и прицеп имеют вместимость по 8 000 л, но после выгрузки прицеп иногда заполнен лишь на 99% — помощник бесконечно стоит на месте.

**Цель:** позволить игроку задать процент заполнения, при достижении которого стандартный AI Worker прекращает ожидание, едет к назначенному пункту разгрузки и затем, если включено повторение задания, возвращается за следующей партией.

**Конкретный пример:** при пороге **95%** прицеп на 8 000 л может отправляться на разгрузку, начиная с **7 600 л** (с учётом допустимых погрешностей представления чисел).

## 2. Объём первой версии (MVP)

1. Изменить логику ожидания загрузки **только у штатного задания `AIJobDeliver` / `AITaskWaitForFilling`**.
2. Добавить одну **глобальную настройку** в игровое меню настроек: **`AI unloading threshold`**.
3. Доступные значения: `80%`, `85%`, `90%`, `95%`, `98%`, `100% (Vanilla)`.
4. Значение по умолчанию: **95%**.
5. Изменение значения в меню применяется к последующим проверкам загрузки **без перезапуска игры**; если задание уже выполняется, настройка начинает действовать при ближайшей безопасной проверке состояния (не отменять начатый переход).
6. Сохранять параметр между запусками игры **в пользовательской папке `modSettings`**, а не внутри ZIP и не в файлах установки FS25.
7. При `100% (Vanilla)` обеспечивать **точно штатную логику**, а не сравнение с `0.9999` и не приблизительную эмуляцию.
8. Мод должен работать без AutoDrive, Courseplay и любых других обязательных модов.

**Не включать в MVP:** индивидуальные пороги для водителей/прицепов/заданий, собственные маршруты, изменения вместимости техники, автоматическую перегрузку из комбайна, настройку по горячим клавишам, изменения экономического баланса.

## 3. Функциональные требования

### 3.1. Определение порога

- Порог применяется к **заполненности участвующих в текущем задании прицепов / fill units**, а не к объёму груза в комбайне.
- Основной показатель для одного fill unit:
  - `fillLevel` — текущий объём;
  - `capacity` — доступная ёмкость (`fillLevel + freeCapacity`, если это корректно для конкретной конфигурации; изучить API).
  - `fillPercent = 100 * fillLevel / capacity`.
- Сравнение: `fillPercent >= configuredThreshold`. Для 8 000 л и 95% это 7 600 л.
- Должно присутствовать **положительное количество груза**; пустой прицеп не может считаться достигшим порога.
- Учитывать только релевантные для данного задания fill units, используя существующую коллекцию `AITaskWaitForFilling.fillUnitInfo` и штатную проверку допустимых fill types.
- Не обходить штатную проверку недопустимого типа груза и обработку ошибок задания.
- Если есть несколько fill units, рассчитывать **суммарную взвешенную заполненность**: `sum(fillLevel) / sum(capacity)` по релевантным ёмкостям. Документировать выбор и проверить на нескольких прицепах; не считать среднее арифметическое процентов, если ёмкости различаются.
- Для нулевой, неопределённой или ошибочной вместимости безопасно использовать ванильное поведение вместо деления на ноль или досрочного отправления.
- Не запускать доставку автоматически из-за некорректного, неизвестного или запрещённого груза.

### 3.2. Переход к доставке

- При достижении порога использовать **штатный переход задания** от ожидания загрузки к поездке на разгрузку.
- Сохранить стандартную задержку ожидания (по опубликованной версии API — около **3 секунд**), а также штатные обработчики `start` / `stop` и `aiPrepareLoading` / `aiFinishLoading`.
- Не телепортировать транспорт, не завершать AI Job целиком и не пропускать стадию выгрузки.
- Циклические задания (`Looping`) должны продолжать работу без ручного вмешательства.
- Повторная проверка на каждом обновлении не должна неоднократно инициировать завершение одного и того же этапа.
- Если в процессе ожидания вручную удалить часть груза и уровень упадёт ниже порога **до фиксации перехода**, поведение должно быть определено и проверено: предпочтительно следовать штатной семантике уже запущенной задержки; избежать зацикливания и двойных переходов.

### 3.3. Настройка в интерфейсе

- В **пункте настроек игры внутри pause menu** добавить понятную строку:
  - Label: `AI unloading threshold`
  - Tooltip: `Minimum trailer fill level before AI delivery starts. 100% restores vanilla behavior.`
  - Options: `80%`, `85%`, `90%`, `95%`, `98%`, `100% (Vanilla)`
- Следовать существующему стилю UI FS25 и обеспечивать управление мышью/клавиатурой.
- Проверить жизненный цикл меню: открытие и закрытие, смена сохранения, повторный вход на карту, повторное открытие настроек. Не создавать дублирующиеся элементы или обработчики.
- В MVP **одна общая настройка для игры**, не требующая изменения каждого задания.
- Если безопасно встроить строку в стандартную страницу нельзя, разрешается отдельная компактная страница/вкладка внутри настроек. Не создавать сторонний внешний UI.
- Локализация MVP: английский язык; архитектура должна позволять добавлять другие языки через стандартный механизм l10n.

### 3.4. Сохранение настроек

- Использовать отдельный XML в `g_modSettingsDirectory` (точный путь и API подтвердить по версии игры); рекомендуемый относительный путь: `FS25_AIUnloadThreshold/settings.xml`.
- Формат может быть, например:

  ```xml
  <aiUnloadThreshold>
      <settings threshold="95" />
  </aiUnloadThreshold>
  ```

- При отсутствии файла, некорректном XML или значении вне списка использовать 95% и не прерывать загрузку карты.
- Сохранять выбранное значение после его изменения; оно должно сохраняться после полного закрытия и повторного запуска FS25.
- Предусмотреть безопасную запись XML стандартными средствами игрового Lua API.
- Не изменять файлы сохранений и не требовать ручного редактирования конфигурации.

## 4. Техническая реализация и ограничения

### 4.1. Перед реализацией обязательно проверить игровой API

Опубликованная документация GIANTS для **FS25 Script v1.20.0.0** показывает:

- `AIJobDeliver.new(...)` создаёт `AITaskWaitForFilling` как этап ожидания загрузки.
- `AITaskWaitForFilling:update(dt)` перебирает `self.fillUnitInfo`; в штатной реализации признак полной загрузки сбрасывается при `freeCapacity > 0`; затем стартует таймер ожидания, и задача завершается.
- `AITaskWaitForFilling` имеет `start`, `stop`, `reset`, `addFillUnits`, `addAllowedFillType`.
- **`AIJobLoadAndDeliver` — другое задание**, использующее `AITaskLoading`, а не `AITaskWaitForFilling`. Нельзя считать эти пути идентичными.

**Нужно:** сверить фактический API с установленной версией FS25 и использовать официальную документацию / доступные игровые Lua-скрипты. Если имена, сигнатуры или жизненный цикл отличаются, скорректировать реализацию и описать расхождения в README. Не копировать вслепую чужие хуки и не придумывать неподтверждённые методы.

### 4.2. Ограничение действия патча

- Хук должен затрагивать **только задачи ожидания у `AIJobDeliver`**. Изменение глобального `AITaskWaitForFilling:update` без проверки типа/принадлежности задания недопустимо.
- Предпочесть минимальный, совместимый со стандартными модами механизм перехвата Lua-метода (через GIANTS `Utils` или аккуратное оборачивание исходной функции — после проверки доступного API).
- При пороге 100% делегировать штатному методу без вмешательства.
- При пороге меньше 100% поддерживать все штатные проверки и последствия (валидация fill type, таймер, ошибка AI, завершение loading task).
- Не переписывать целиком AI Job, не заменять его маршрутизацию и не использовать постоянный polling всех машин в мире.
- Обрабатывать отсутствие нужного класса / функции защитно: написать предупреждение в лог и сохранить ванильное поведение.
- Вызовы, меняющие AI Job, выполнять только на авторитетной стороне (server / single-player game server), чтобы не вызывать дублирование в multiplayer-контексте.

### 4.3. Совместимость

- Платформа приёмки — **macOS**, версия игры — **FS25**.
- В первой версии **официально поддерживается одиночная игра**. Multiplayer / dedicated server не считать проверенными, если нет тестов; не объявлять их поддержку без реализации синхронизации параметра и проверки серверного авторитета.
- Не требовать GIANTS Editor для использования готового ZIP. Разработка может использовать его или локальную документацию при наличии.
- Не записывать изменения в папку установки FS25 и не менять игровые Lua-файлы.
- Поддержка модифицированных или нестандартных прицепов — best effort; проблемы должны логироваться, а не ломать сохранение.

## 5. Структура проекта и артефакты

Рекомендуемая структура (можно адаптировать к проверенному FS25 SDK):

```text
FS25_AIUnloadThreshold/
├── modDesc.xml
├── scripts/
│   ├── main.lua
│   ├── UnloadThreshold.lua
│   ├── Settings.lua
│   └── SettingsUI.lua
├── gui/                 # Only if custom UI assets are required
├── l10n/                # Optional localization resources
├── README.md
└── build.sh
```

Требуемые результаты:

1. Исходный код мода в указанной или аналогичной структуре.
2. Готовый `FS25_AIUnloadThreshold.zip`, пригодный для копирования в `mods`.
3. `README.md`: установка, выбор настройки, поддерживаемые задания, ограничения, удаление мода, диагностика по `log.txt`.
4. Простой скрипт сборки ZIP для macOS (`build.sh`), проверяющий, что **`modDesc.xml` лежит в корне архива**, без дополнительной внешней папки.
5. Краткий отчёт о проверках: что подтверждено статически, что реально проверено в игре, что не удалось проверить.

Для macOS путь установки обычно:

```text
~/Library/Application Support/FarmingSimulator2025/mods/
```

**Строки, идентификаторы, комментарии и сообщения логирования в коде — на английском языке.** Само ТЗ и README могут быть на русском.

## 6. Критерии приёмки

| № | Сценарий | Ожидаемое поведение |
|---|---|---|
| 1 | Новая установка, настроек ещё нет | В меню отображается 95%; игра запускается без ошибок |
| 2 | Прицеп 8 000 л, порог 95%, загружено 7 599 л | Водитель продолжает ждать |
| 3 | Прицеп 8 000 л, порог 95%, загружено 7 600 л | После штатной задержки водитель начинает рейс на разгрузку |
| 4 | Прицеп 8 000 л, порог 95%, загружено 7 920 л (99%) | Водитель не зависает в ожидании 100% |
| 5 | Порог 100%, заполнение 99% | Полностью ванильное поведение: водитель продолжает ждать |
| 6 | Порог 100%, заполнение 100% | Штатное отправление после штатной задержки |
| 7 | Пустой прицеп, порог 80% | Водитель не отправляется |
| 8 | Загрузка неподходящего груза | Не обходится штатная ошибка/валидация AI |
| 9 | Включено повторение задания | Разгрузка завершается, водитель возвращается к месту загрузки и снова ждёт порога |
| 10 | Изменили настройку 95% → 90% | Значение применяется без перезапуска; новые проверки используют 90% |
| 11 | Закрыли и запустили игру снова | Сохранённое значение настройки восстановлено |
| 12 | XML отсутствует / повреждён / значение вне диапазона | Безопасный fallback на 95%, без падения игры |
| 13 | Несколько прицепов разной ёмкости | Порог считается от суммарной ёмкости участвующих fill units; нет деления на ноль |
| 14 | Стандартное полевое задание или обычное вождение AI | Поведение не изменяется |
| 15 | Повторная загрузка карты / повторное открытие меню | UI не дублируется; хук не устанавливается повторно |
| 16 | Выбран порог 100%, мод включён | Поведение максимально идентично игре без мода |

**Обязательный реальный тест при наличии FS25:** сценарии 3–6 и 9 на macOS. Если Codex не имеет доступа к запущенной игре, он должен явно отметить эти сценарии как **не проверенные в игре**, а не заявлять их успешное прохождение по итогам статического анализа.

## 7. Диагностика и качество

- Отсутствие Lua errors и XML errors в `log.txt` при загрузке мода, входе на карту, изменении настройки и выполнении задания.
- Однократное информационное сообщение в лог о загрузке мода и текущем пороге; не писать сообщение каждый кадр.
- Никаких глобальных побочных эффектов для других AI-заданий.
- Никаких дополнительных расходов, ускорения техники, изменения объёма урожая или вместимости.
- Не копировать в проект исходные файлы GIANTS целиком: использовать минимальный патч и документировать назначение перехвата.
- Желательно вынести чистую функцию расчёта порога для локального unit/smoke тестирования без запуска игры; покрыть края 0, 95%, 99%, 100%, разные ёмкости и отсутствие ёмкости.

1. Изучить структуру текущего репозитория, если она существует; если репозиторий пуст, создать проект с нуля.

4. Реализовать интерфейсную настройку и сохранение в `modSettings`.
5. Добавить защитные проверки, README и скрипт сборки.
6. Выполнить доступные статические тесты и собрать ZIP; проверить его структуру.
7. При наличии установленной игры провести ручное тестирование по таблице приёмки и изучить `log.txt`.

**Важное правило:** при неполноте документации сначала найти и подтвердить точку интеграции, а не подменять её произвольным неработающим кодом. Если интеграция UI оказывается несовместимой с текущей версией игры, документировать причину и предложить безопасный fallback, сохранив работоспособность основной логики.
